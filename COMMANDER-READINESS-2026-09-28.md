# Jester commander readiness review

September 28, 2026. This reviews the whole path from Drew's voice to EBI work. It supplements the [trial failure review](REVIEW-jester-trial-2026-09-28.md). The goal is the existing [handoff](HANDOFF.md): Drew talks naturally, Jester understands and checks the request, and the right EBI session does the computer work. Guest control remains out of scope. This is a plan; these outcomes are not yet proven live.

## Where the recorded trial went wrong

The room transcript around **13:55 CDT** records Drew asking for a Jobs/LinkedIn session over several turns. Jester answered conversationally, but the current create parser requires a project and a first task in one sentence. EBI's API journal has **no spoken-task or spawn POST** during the recorded 13:55–14:43 trial. The log therefore gives no evidence that Jester created that session or handed off work. The trial did not exercise a successful real EBI action.

Around **14:42 CDT**, Drew asked for help with his audit and corrected the name to Zoro. Jester answered as if it did not know the audit. Zoro is present in the live EBI session snapshot, but the request did not match Jester's exact status/task grammar, so the checked session facts never reached Luna. “Yo Jester” is accepted by the conversation gate but not stripped by the owner-intent parser, another route miss for ordinary speech.

Around **14:27–14:32 CDT**, speech recognition hit its ONNX memory limit 78 times. During the same room visit Jester spoke over side conversation, ignored natural leave requests, and logged one overlapping Luna turn. These are commander blockers: a wrong or partial transcript must never become a task, and an owner must be able to make Jester stop immediately. The detailed evidence and repairs are in the trial review.

The current logs show spoken replies and timing, plus API HTTP requests, but **no per-request trail** of final recognized words → chosen intent → resolved thread ID → posted request ID → receipt → worker state. This means a future failure could still be hard to distinguish from a missed wake, parser miss, stale tag, API timeout, or an EBI worker that never started.

A pure replay against today's parser returned **no owner intent** for the recorded multi-turn LinkedIn request, the Zoro audit question, “Yo Jester, what is Zoro doing?”, “Disconnect,” and “Jester, shut up, go away.” The same parser does recognize the narrow form “Jester, tell Zoro to review the audit.” This confirms a routing gap without making a paid model call or touching an EBI session.

## What works in code, and what is still missing

| Commander step | Present now | Gap to close |
| --- | --- | --- |
| Hear only the right request | Owner-only wake/follow-ups, per-speaker transcript, just-listen, barge-in | Recognition memory errors silently discard input; 60-second follow-up accepts side conversation; leave phrases are too narrow; just-listen mode is in memory and can reset after a service restart. |
| Understand the whole thought | Fast parser for specific status, send, create, stop, close, model, history and watch forms | Natural phrasing and a request spread across several turns often fall into ordinary Luna chat. The parser cannot consistently collect a project, destination and task through pauses/corrections. |
| Find the exact destination | Current tags/aliases, project catalog, exact string thread IDs, stale-tag checks | EBI caps Jester's session snapshot at 100 with no continuation; it returned exactly 100. Historical and natural project/topic references need checked search, with clarification only for real ambiguity. |
| Send work once | EBI has at-most-once spoken receipts and spawn correlation; clear one-sentence commands use them | Jester creates a fresh operation ID inside each call without saving it before the POST. After a crash or uncertain response it cannot reconstruct the exact operation. No real voice-to-thread delivery has been verified in this trial. |
| Tell Drew what happened | Exact command path distinguishes accepted, posted and failed; result watches use turn evidence | A new-session answer says “started” before checking the first turn actually ran. “Update me on my sessions” currently lists only up to five names, not each task, progress or blockers. A generic Luna reply can sound confident while lacking EBI facts. |
| Keep working after restart | Service restarts, EBI owns durable threads, requested dependencies/results persist | Jester's pending conversational request and bound target are in memory; transcript files can stay marked “in progress”; just-listen needs safe restoration. Restart should reconcile operation IDs and EBI state before speaking or sending anything again. |

## Build the commander as one checked loop

1. **Make every voice turn traceable.** Log a local correlation ID, speaker/mode, recognition outcome, intent decision, canonical target ID, action ID, EBI receipt and final spoken status. Keep transcripts and secrets out of routine logs; link to the already stored transcript when needed. Add a replay harness for the actual trial utterances. A replay must show why the LinkedIn request and Zoro question were not routed, before changing their handling.
2. **Make hearing and the attention gate dependable.** Fix the GPU arena failure with a bounded recognition strategy and automatic recovery; test long and short speech under normal EBI load. Have guest speech end Drew's follow-up window, use a short owner follow-up after Jester's reply, and recognize the observed dismissal phrases locally. Restore just-listen silently after a service restart if Drew is still in the room. No missed/uncertain speech may trigger an EBI action.
3. **Collect one complete owner instruction before any side effect.** Keep exact commands as fast paths. For natural phrasing, use Luna only to propose a small typed intent such as `answer`, `status`, `send`, `create`, `stop`, `close`, `runtime`, `history`, or `watch/dependency`; application code validates owner, mode, target, task, risk and finality. Keep a pending draft across owner turns so “open a Jobs session ... for LinkedIn ... here is the task” becomes one operation; the latest correction wins. Support an explicitly requested empty thread without inventing a seed task; EBI's current `/api/spawn` requires a prompt, so this needs a narrow EBI change. Never execute a partial draft or invented detail. A request for computer work should reach this route before Luna can answer generically that it lacks file or Discord access.
4. **Resolve and execute against EBI truth.** Add a complete current-session lookup beyond 100 entries or an exact-tag endpoint, plus checked topic/project search. Bind the selected thread ID, recheck it at send time, and persist the operation ID and final prompt before POST. Reconcile the same ID after a timeout/restart; never silently retry with a new ID. Check that a new session's first turn actually queued/runs before saying it started. Keep clear, owner-authorized work automatic without a readback ritual.
5. **Answer status from evidence and stay quiet otherwise.** On request, give a concise spoken summary of current tasks and blockers, with a fuller labeled list in Auto Transcripts when many sessions are active. Distinguish created, accepted, posted, running, completed, failed and unknown. For open-ended “help me with Zoro” questions, give Luna only fresh, exact EBI facts and relevant visible thread context; do not let it invent a project status. Routine changes remain silent unless Drew explicitly requests a result watch.
6. **Prove the loop in a disposable live session.** First replay recorded utterances against fake EBI data, including corrections, >100 sessions, guest speech, mode changes, timeouts and restart. Then Drew makes one harmless spoken request to a disposable thread: compare recognized words, final prompt, exact thread ID, durable receipt, first-turn state, spoken confirmation and later on-demand status. Try multi-turn creation, a correction, follow-up reference, stop, just-listen, leave and service restart. Do not use a real working thread as the first action target.

V1 must cover the owner's normal session workflow: find a current or past thread by tag, project or topic; ask what it is doing; create a session in a real project with the requested backend and first task, or explicitly open an empty one; send faithful follow-up work; stop or close an exact session; request a simple “when this finishes, tell that one” handoff or one-time result watch; and ask for results when wanted. EBI sessions keep working if Jester leaves or restarts. Jester is the voice controller for these actions. EBI sessions, not Luna, perform file, browser, command and project work.

The first two outcomes make Jester safe and understandable in the room; outcomes three through five make it an actual commander. Each should be split into 15–30-minute checked changes in Jester and, where needed, a separately coordinated EBI slice. The earlier **3–5 hour estimate covered only the visible trial bugs**. The complete commander loop is more likely **one to two working days of implementation and checks, then Drew's 10–15-minute real-use trial**. This is a planning estimate, not a readiness promise.

## Acceptance rule

Jester is ready for Drew to use on real projects only after it can take a natural, corrected spoken task, send **one faithful prompt to the exact chosen EBI thread**, show a verifiable receipt, answer later status from that thread's real state, recover safely from a restart, and stay silent when Drew is talking to someone else or says just listen/leave. Automated checks alone cannot prove the final voice behavior; Drew's trial decides the remaining feel issues.
