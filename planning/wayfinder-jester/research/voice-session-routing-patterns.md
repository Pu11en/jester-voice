# Voice-to-session routing patterns — primary-source research (2026-09-28)

Scope: Drew's spoken commands to his existing EBI sessions. These are design and acceptance-test recommendations, not claims that Jester already implements them. The local [voice-to-EBI audit](voice-to-ebi-handoff.md) describes the current endpoint gaps.

## Patterns to carry into Jester

1. **Treat a name as a lookup key, not the destination.** Resolve `Frankie`, current aliases, and any spoken project/thread label against a fresh, read-only session catalog. Bind the resulting **exact thread ID** as a string for the whole request; revalidate that ID and the real speaker before sending. Discord distinguishes thread `id`, `parent_id`, name, and (for forum threads) `applied_tags`; its 64-bit snowflakes are returned as strings to avoid integer overflow. Thus a display name or tag alone is inadequate as delivery identity. This is an inference for Jester from Discord's object model. [Discord channel object](https://docs.discord.com/developers/resources/channel#channel-object), [Discord snowflakes](https://docs.discord.com/developers/reference#snowflakes).

2. **Hold a small pending dialog until destination and task are both settled.** Model fields such as `target`, `action`, `instruction`, and `clarification_needed`. A correction replaces the earlier value before dispatch: “Frankie—actually Zoro…” must produce one request to Zoro. Ask only about a missing or conflicting target; avoid mandatory readback for every clear instruction. Alexa's dialog model explicitly collects, validates, corrects, and optionally confirms slot values across turns. OpenAI's voice guidance says never call tools with guessed or ambiguous exact values. [Alexa dialog management](https://developer.amazon.com/en-US/docs/alexa/custom-skills/dialog-interface-reference.html), [OpenAI exact-value guidance](https://developers.openai.com/api/docs/guides/voice-prompting).

3. **Keep conversational reference state separate from addressability.** “Tell him to add tests” may refer to the last *bound* thread during Jester's 60-second follow-up window; after timeout, a new wake and a clear target are needed before dispatch. A later unrelated name mention must not silently retarget pending work. Preserve current task state across a voice-session restart, then check backend status before any resend. OpenAI recommends preserving application task state and checking outstanding operations on resume. This is a Jester-specific application of that guidance. [OpenAI Live session continuity](https://developers.openai.com/api/docs/guides/live-conversations).

4. **Use typed tool boundaries and an idempotency key.** The model may propose a structured `resolve`/`send` action, but application code must check speaker authority, target ID, and mode before the side effect. OpenAI describes tool calls as requests whose input is executed by application code and recommends strict schemas; its Live guidance says permissions and confirmations belong in application code. Give each finalized spoken instruction a stable operation ID; retry the *same* ID and payload after an uncertain response, reject the same ID with different payload, and return the original receipt. Stripe and AWS document this pattern. Discord warns events can be missing or repeated, so event arrival alone is not a delivery guarantee. [OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling), [OpenAI Live controls](https://developers.openai.com/api/docs/guides/live-conversations), [Stripe idempotency](https://docs.stripe.com/api/idempotent_requests), [AWS ECS idempotency](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/ECS_Idempotency.html), [Discord consistency](https://docs.discord.com/developers/reference#consistency).

5. **Report the stage actually verified.** Keep distinct receipts for `accepted`, `queued`, `delivered/started`, `completed`, `failed`, and `unknown`; say the exact session name when work is accepted. HTTP 202 explicitly means processing has *not* completed. If the send times out, report “I can't verify whether Frankie received it” until a same-ID receipt/status lookup resolves it; never infer success from the voice model's own reply. [RFC 9110 §15.3.3](https://www.rfc-editor.org/rfc/rfc9110#section-15.3.3), [OpenAI Live task IDs and status](https://developers.openai.com/api/docs/guides/live-conversations).

## Small acceptance set focused on wrong-thread and duplicate-work failures

| Spoken scenario | Required observable result |
| --- | --- |
| “Jester, Frankie, we need to fix the prompt navigation”; then add a detail before turn finalization | One faithful instruction with both details, sent once to Frankie's current exact ID. |
| “Frankie—no, Zoro—fix that navigation” | Zero Frankie sends; one Zoro send. Final corrected destination wins. |
| Two active sessions share `Frankie` or an alias, or the tag was reassigned | Ask which session; zero sends until the exact ID is selected. |
| “Tell him to add tests” within 60 seconds of an accepted Frankie request | Resolve only to the last bound Frankie ID; if no reliable bound target exists, ask. |
| Same pronoun request after the 60-second lapse, or while `Jester just listen` is active | Zero sends. Wake and identify the destination again after the lapse; `just listen` remains transcript-only. |
| Speech mentions “Frankie” in a side conversation, or STT is unsure whether the name is Frankie | Zero sends; ask only if Drew clearly addressed Jester with a task. |
| Send receives 202, then connection drops before a final receipt | Say “accepted/unknown” according to evidence; same operation ID retry or lookup yields one backend task and one thread post. |
| Duplicate callback/replayed audio/restart repeats the same finalized turn | One operation ID, one destination post, one task start. |
| Frankie accepts a task and later fails | First say accepted/queued; later say failed with verified reason. Never say “done” on initial acceptance. |

The first two examples mirror Drew's intended “tell Frankie what to do” flow; the rest target the failure modes implied by the cited platform behavior and the local handoff audit. These tests should run against fake catalog, STT, and EBI receipts before a supervised live pass, with assertions on **zero or one side-effecting send** and its exact string thread ID.
