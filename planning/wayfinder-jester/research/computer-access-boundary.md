# Jester's computer-access boundary — research, 2026-09-28

## Question and recommendation

**Recommendation: choose A for computer work, with a narrow read-only status exception.** Jester should be the voice interface and policy gate. Its local code may query purpose-built, read-only EBI status/history endpoints and handle its own transcripts and health, but Luna should have no general shell, arbitrary file read/write, desktop, browser, or broad MCP tool. When Drew asks for computer work, Jester should resolve the exact project and EBI session, authorize the speaker, then send the task to EBI through a typed action. EBI's agent then does the computer work under the existing EBI harness and reports the result. This is an architectural recommendation, not a claim that today's EBI API already enforces every boundary.

This fits [Jester's mission and identity rules](../../../HANDOFF.md), which require a natural, powerful voice interface; deterministic checks based on Discord user identity; and real EBI state instead of Luna's memory. It also fits [the measured Codex bridge](../../../bench/BRAIN_RESULTS.md): disabling apps, browser, and computer use made four warm first-word samples 1.0–2.1 seconds, versus 1.2–11.1 seconds in four default samples. The sample is too small to promise a speed gain, but it is evidence that a lean brain can preserve conversational speed while EBI handles work.

The boundary has a practical meaning: **“Ask Zoro to fix the login bug” still works.** Jester sends that request to the selected EBI thread. **“What is Zoro doing?” also works** through a read-only, typed EBI status call; it should not require launching a new agent turn. The boundary governs *where* computer execution occurs, not whether voice can request it.

## Evidence from primary sources

- [OWASP LLM06:2025 Excessive Agency](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/) identifies excessive functionality, permissions, and autonomy as separate risks. It recommends minimal extensions, granular functions instead of open-ended commands, least-privilege downstream identities, and approval for high-impact actions. This supports using narrow EBI tools at Jester's boundary and keeping arbitrary shell out of Luna's tool surface.
- [OWASP LLM01:2025 Prompt Injection](https://genai.owasp.org/llmrisk/llm01-prompt-injection/) warns that user prompts and retrieved material can steer a model into unauthorized tool use; it recommends authorization in code, restricted privileges, and treating external material as untrusted. **Inference for Jester:** in a shared voice room, a spoken “ignore the rules” or a malicious file read through EBI must remain data, never a permission grant.
- [OpenAI's agent guardrails and human review guide](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals) says tool guardrails belong at the side-effecting tool boundary, because agent-level input/output checks do not cover every call. It recommends checking target, action, arguments, and calling identity, and pausing ambiguous or high-risk actions. Jester's typed action check and EBI's own authorization should both inspect the same actor and canonical thread ID.
- [OpenAI's function-calling guide](https://developers.openai.com/api/docs/guides/function-calling) recommends structured parameter schemas, enums that prevent invalid states, and keeping the available tool set small. [OpenAI's programmatic-tool-calling guide](https://developers.openai.com/api/docs/guides/tools-programmatic-tool-calling) additionally says to check arguments and permissions on every call in the application and keep writes or approval-sensitive actions on a clear direct-call boundary. This supports `get_session_status(thread_id)` and `send_session_message(thread_id, text)` rather than model-authored shell strings.
- [OpenAI's computer-use guide](https://developers.openai.com/api/docs/guides/tools-computer-use) recommends an isolated environment, site/action allowlists, treating on-screen text as untrusted, confirming consequential actions, bounding a run, and verifying outcomes. If Jester ever gets direct desktop control, it would need a separate execution sandbox and policy surface; the current voice service has neither.
- [Discord's official Voice Connections specification](https://github.com/discord/discord-api-docs/blob/main/developers/topics/voice-connections.mdx) and [Gateway Events specification](https://github.com/discord/discord-api-docs/blob/main/developers/events/gateway-events.mdx) provide user and voice-state identifiers at the transport layer. Jester should take speaker identity from the Discord receive path and never from what a voice transcript claims. This is an inference applied to the local design, not a statement that speech recognition proves speaker identity.

## Comparing the four choices

| Choice | Benefit | Cost or risk | Fit for Jester |
| --- | --- | --- | --- |
| **A. EBI performs computer work** | One existing place for project context, execution, session history, and recovery; Jester stays a fast voice interface. | EBI must expose stable typed status/action APIs and enforce the caller's identity; some long jobs take an extra handoff. | **Best default.** Use Jester's local typed read-only EBI lookups for quick status, and EBI sessions for actual work. |
| **B. Jester directly reads local files/status** | Could answer a narrow diagnostic question quickly without a new EBI turn. | An “arbitrary read-only” file tool can expose secrets or private project content to room guests, and create a second source of project truth. | Permit only named, purpose-built health/status reads already authorized for the speaker; prefer EBI's read-only API over raw filesystem reads. |
| **C. Jester directly changes routine files/apps** | Simple actions may appear faster and can continue while EBI is busy. | Duplicates EBI's project context, permission, rollback, and audit logic; “routine” has no stable boundary for a speech-driven system. | Defer unless a specific action is measured to need it; then add one typed capability with a fixed scope, not general file/app control. |
| **D. Jester runs unrestricted commands** | Maximum expressive power in one hop. | A misheard instruction, guest speech, or prompt injection can become arbitrary code with the voice service's machine privileges. This is the broad tool pattern OWASP recommends avoiding. | Do not add. Send broad work to an EBI agent whose scope and outcome can be tracked. |

The risk comparison follows the cited OWASP/OpenAI guidance. The performance and maintainability claims are design inferences; there is no local benchmark comparing the four choices end to end.

## Minimum implementation contract

1. **Identity and authorization:** attach the real Discord speaker user ID to every accepted turn; code checks owner/guest and any temporary grant. A guest saying “I am Drew” cannot change that identity. Guests receive no private EBI status by default, per [HANDOFF](../../../HANDOFF.md).
2. **Typed tools:** Luna can propose an intent, exact canonical thread ID, and small typed arguments. Jester validates them only after the speaker finishes/corrects the turn. It never executes model-authored shell text. Read results are filtered to the speaker's allowed scope before they enter Luna or spoken output.
3. **EBI boundary:** authenticate Jester to EBI and make EBI re-check actor, scope, and exact thread ID for each privileged endpoint, especially guest delegation. The [EBI interface inventory](../../../EBI_INTERFACES.md) reports that bearer auth is absent in the live configuration, `/spoken` accepts only the owner, and `/close` trusts an arbitrary actor string. A 2026-09-28 read-only check confirmed the local `.env` has no nonempty `CCDB_API_SECRET` entry and `GET /api/tasks` returned 200 even with a deliberately invalid bearer token. These are gaps to close before guest control; do not impersonate Drew on behalf of a guest.
4. **Action policy:** ordinary reads and low-impact owner requests proceed without a ritual. Clarify ambiguous targets or broad destructive intent; require explicit owner confirmation for genuinely high-impact, hard-to-reverse actions, consistent with [HANDOFF](../../../HANDOFF.md) and OpenAI's [tool-boundary guidance](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals).
5. **Verification:** return the real EBI receipt/status, preserve a correlation ID to avoid duplicate side effects after retries, and report uncertainty instead of claiming completion from Luna's text. Test guest impersonation, forged model tool output, expired/wrong-session grants, reused Zoro/Nami tags, mid-sentence corrections, and EBI timeout/restart.

## Decision for the overnight plan

Adopt **A with the narrow status exception** in the plan: Jester may call authenticated, typed read-only EBI APIs itself; EBI sessions perform file, app, browser, shell, and project work. This keeps Drew's voice interface powerful while preserving one execution authority. The full guest-control promise still depends on closing the EBI authorization gaps, and Drew's live conversation test remains necessary to judge the experience.
